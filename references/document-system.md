# Document System

## The 6 Document Types

| Type | Prefix | Directory | Author | Requirement linkage |
|---|---|---|---|---|
| Product requirements | PRD | docs/prd/ | pm | One-to-one |
| Technical specification | SPEC | docs/spec/ | architect | One-to-one (paired by number) |
| Test plan | TEST-PLAN | docs/test-plan/ | qa | One-to-one (paired by number) |
| Architecture decision | ADR | docs/adr/ | architect | Independent numbering, major decisions only |
| Runbook | RUNBOOK | docs/runbook/ | dev | Independent numbering, production modules |
| Global progress | STATUS | root STATUS.md | Auto-generated by script | Aggregates all requirements |

**ID-pairing rule**: a single requirement runs through multiple documents, all using **the same number**:

```
The requirement "user points-deduction" maps to:
  PRD-008.md       ← produced by pm
  SPEC-008.md      ← produced by architect
  TEST-PLAN-008.md ← produced by qa
  tests/e2e/PRD-008.spec.ts  ← E2E written by qa
```

ADR and RUNBOOK use independent numbering (e.g. ADR-001, RUNBOOK-001) and can be referenced by multiple requirements.

### A PRD must contain 4 sections

The PRD written by the PM is a comprehensive document:

1. **Feature definition**: user stories, acceptance criteria, feature list
2. **Prototype design**: UI sketches (ASCII or Figma links)
3. **Business flow**: Mermaid flowchart
4. **Data flow**: Mermaid flowchart LR (nodes are data, edges are transformations)

For simple features, some sections may be "not applicable", but you must explicitly state "this feature has no complex business flow".

### A SPEC must contain

The SPEC written by the architect comprehensively contains:

- Technical approach overview
- Architecture diagram (Mermaid)
- API design (shared between frontend and backend)
- Data model (if new tables are introduced)
- Technical implementation of the business flow
- Implementation task breakdown (including frontend/backend division of labor)
- Risks and mitigations

### Frontmatter (the stage field is key)

Every document must have:

```yaml
---
id: PRD-008              # globally unique
title: User points-deduction
type: prd                # prd | spec | adr | test-plan | runbook
stage: pm-designing      # current stage; the STATUS script aggregates based on this
owner: pm
created: 2026-05-10
updated: 2026-05-15
summary: One-line summary (< 100 chars)
---
```

Optional: `related`, `tags`, `module`, `priority`, `cancelled-reason`.

### The stage enum (8 stages + special)

| stage value | Meaning | Currently responsible |
|---|---|---|
| `pending` | Awaiting kickoff | - |
| `pm-designing` | PM is designing | pm |
| `awaiting-prd-approval` | Awaiting user approval of the PRD | user |
| `architect-designing` | Architecture design in progress | architect |
| `awaiting-spec-approval` | Awaiting user approval of the technical approach | user |
| `developing` | Development in progress | frontend + backend |
| `testing-round1` | Round 1 testing in progress | qa |
| `fixing` | Fixing in progress | frontend/backend |
| `testing-round2` | Round 2 retesting in progress | qa |
| `awaiting-deploy-approval` | Awaiting user approval to deploy | user |
| `deployed` | Deployed ✅ | - |
| `cancelled` | Cancelled ❌ | - |

### Required before writing a document

1. Call librarian to search whether a document on the same topic already exists
2. Take the highest existing ID of the same type and add 1
3. Pick a template from `docs/_templates/`
4. **After finishing, you must update the stage field and run build_status.py**

### Modification rules

- Modifying the body text requires updating the `updated` field
- Major changes to documents in the approved/active stage must go through a process similar to creating a new one
- Do not delete documents; archive via the `cancelled` status
- IDs are never reused

## Document-volume scaling strategy

The current default is "Stage A" (flat layout). It evolves naturally with document volume:

| Document count | Mode | Trigger | Upgrade action |
|---|---|---|---|
| 0-20 | Flat layout + auto index | Current | - |
| 20-50 | + tags + related | librarian search is inaccurate | Populate the extended fields |
| 50-100 | Subdirectories by module | Too many files in a single directory | Configure the module field |
| 100+ | Upgrade to the full system | Continuous growth | See the v1.1 advanced guide |

```

## Required frontmatter fields

```yaml
---
id: <PREFIX>-<3 digits>
title: Short title
type: prd | spec | adr | test-plan | runbook
stage: pending | pm-designing | awaiting-prd-approval | architect-designing | awaiting-spec-approval | developing | testing-round1 | fixing | testing-round2 | awaiting-deploy-approval | deployed | cancelled
owner: <agent-name>
created: YYYY-MM-DD
updated: YYYY-MM-DD
summary: One-line summary (< 100 chars)
---
```

## Full stage enum description

| stage | Meaning | Who may set this status |
|---|---|---|
| `pending` | Awaiting kickoff | pm (at creation) |
| `pm-designing` | PM is designing | pm |
| `awaiting-prd-approval` | Awaiting user approval of the PRD | pm on completion |
| `architect-designing` | Architecture design in progress | architect |
| `awaiting-spec-approval` | Awaiting user approval of the technical approach | architect on completion |
| `developing` | Development in progress | frontend or backend on kickoff |
| `testing-round1` | Round 1 testing in progress | qa |
| `fixing` | Fixing in progress | qa (when a failure is found) |
| `testing-round2` | Round 2 retesting in progress | qa |
| `awaiting-deploy-approval` | Awaiting user approval to deploy | qa (when retesting passes) |
| `deployed` | Deployed | marked by pm after deployment |
| `cancelled` | Cancelled | pm (when the user decides not to proceed) |

**Key rule**: once marked `awaiting-*-approval`, you must wait for user approval; agents must not advance on their own.

## Required before creating a document

1. Call librarian to search whether one already exists
2. Take the highest ID of the same type + 1
3. Copy a template from `docs/_templates/`
4. Fill in the complete frontmatter

## Required after modifying

1. Update the `updated` field
2. If the stage was modified, run `python scripts/build_status.py`

## Cross-document references

Use IDs (e.g. `PRD-008`), not natural language. The optional `related` field lists linkages:

```yaml
related: [SPEC-008, ADR-005]
```

## Don'ts

- Do not delete documents (archive via cancelled)
- Do not reuse IDs
- Do not write the same content across multiple documents
- Do not write "to be filled in" (either omit it, or state "pending decision by X, expected to be added by Y")
